# 피싱 도메인 사례 — gowid.co.com

대화하며 다룬 내용만 여기에 정리한다.

## 상황

- 정상 사이트: **gowid.com**
- 누군가 만든 피싱 서버: **gowid.co.com**
- 조사 결과: `gowid.co.com` 은 **Cloudflare** 를 앞단에 두고 **Railway** 호스팅으로 운영 중.

---

## 1. 왜 하필 `gowid.co.com` 인가 — 도메인 혼동 공격

핵심은 **"진짜처럼 보이는 가짜 주소"** 를 만드는 것.

- 정상 `gowid.com` → 등록 도메인이 `gowid.com`, 우리 소유.
- 가짜 `gowid.co.com` → **등록 도메인은 `co.com`** 이고, 그 밑에 `gowid` 를 제3자가 붙인 것.

함정은 `co.com` 이 **아무나 돈 주고 살 수 있는 상용 도메인 서비스**라는 점.
공격자는 `gowid` 를 서브도메인처럼 붙여 `gowid.co.com` 을 만들 수 있다. 우리 소유가 전혀 아니다.

사람 눈에 위험한 이유:
- 한국 사용자는 `naver.co.kr` 처럼 **"co" 가 들어간 주소를 오히려 공식처럼** 느낀다.
- `gowid.co.com` 을 쓱 보면 "gowid 의 .com 공식 사이트" 로 착각하기 쉽다.

보안 용어:
- **Typosquatting** (타이포스쿼팅): 오타 노림 — `gowdi.com`, `gwoid.com`
- **Combosquatting** (콤보스쿼팅): 브랜드명 + 추가 문자/단어 — `gowid-login.com`, `gowid.co.com`

`gowid.co.com` 은 콤보스쿼팅 + "진짜 도메인 계층을 흉내 낸" 케이스.

---

## 2. 공격자가 얻으려는 것 (동기)

gowid 가 **법인카드·지출관리 핀테크**라서 돈·금융 계정과 바로 연결된다.

1. **로그인 정보 탈취 (credential phishing)** — 가장 흔함.
   로그인 화면 복제 → ID/PW 입력 → 탈취 → 진짜 계정 침입 → 자금 이체·카드·재무정보 접근.
2. **금전 사기** — 가짜 결제/송금/카드정보 입력 유도.
3. **멀웨어 배포** — 가짜 앱/파일 다운로드 유도.
4. **브랜드·평판 공격** — 고객 신뢰 악용, 사고 시 gowid 평판 손상.
5. **트래픽 가로채기** — 아래 구글 광고와 직결.

---

## 3. 구글 광고와의 연결

공격자가 흔히 쓰는 수법:
- **Google Ads(검색광고) 구매** → "gowid" 검색 시 **맨 위 광고 자리에 피싱 사이트** 노출.
- 사용자는 광고/공식 구분 못 하고 클릭 → `gowid.co.com` 유입 → 피싱.

그래서 Google 쪽 신고가 두 갈래:
- **Google Safe Browsing 신고** → 브라우저(Chrome/Safari/Firefox) 차원 "위험 사이트" 경고.
- **Google Ads 정책 위반 / 상표권 침해 신고** → 광고 자체를 내림.

---

## 4. 트래픽 구조와 대응 계획 해설

먼저 트래픽 구조를 이해하면 대응이 전부 풀린다.

```
사용자 → [DNS: gowid.co.com] → Cloudflare (앞단 프록시/CDN) → Railway (실제 호스팅 서버)
```

| 구성요소 | 역할 | 왜 신고 대상인가 |
|---|---|---|
| **Cloudflare** | 리버스 프록시/CDN. 실제 서버 IP를 **가려주는 앞단**. 호스팅 아님 | 경유 차단/경고, 때로 진짜 origin(Railway) 정보 전달 |
| **Railway** | 앱이 **실제로 돌아가는 호스팅 플랫폼(PaaS)** | 콘텐츠를 실제로 서빙 → **여기 내리는 게 가장 근본적** |
| **Google Safe Browsing** | 브라우저 위험 사이트 DB | 사이트가 안 내려가도 **사용자 접근 차단** |

담당자 계획을 쉽게 풀면:
> "진짜 서버는 Cloudflare 뒤에 숨어 있는데, 캐보니 실제 호스팅은 **Railway** 더라.
> 그러니 **Railway에 사칭·무단복제 abuse 신고**해서 계정을 정지시키면 사이트가 내려간다.
> 동시에 **Cloudflare**(앞단)와 **Google Safe Browsing**(브라우저 경고)에도 신고해,
> 내려가기 전까지 사용자 피해를 막는다."

---

## 5. "막는다" 는 구매가 아니다 — takedown vs 예방

흔한 오해: "gowid.co.com 을 사서 막는다"

- `gowid.co.com` 은 **이미 공격자 소유**라 애초에 살 수 없다 (도메인은 선점 소유제).
- 공격자에게 **돈 주고 사면 안 된다** — 보상이 되어 재등록을 유도, 끝이 없다. 협상이 아니라 신고 대상.

우리는 그 도메인에 직접 손댈 권한이 없으므로, **도메인을 작동하게 해주는 중간 사업자들에게 레버리지**를 건다.

| 막는 방법 | 신고 대상 | 효과 | 난이도 |
|---|---|---|---|
| **콘텐츠 내리기** | Railway (호스팅) | 사이트가 에러/빈 페이지. 도메인은 살아있지만 보여줄 게 없음 | ⭐ 가장 빠름 |
| **브라우저 경고** | Google Safe Browsing | 접속 시 "위험 사이트" 경고 → 사용자 못 들어감 | ⭐ 즉효 |
| **도메인 자체 정지** | `co.com` 운영사 / registrar | DNS 자체가 안 뜸. 근본적이지만 abuse·상표 증명 필요 | ⭐⭐⭐ |
| **도메인 강제 회수** | UDRP (도메인 분쟁 해결 기관) | 법적 절차로 **도메인을 우리에게 이전**. 구매❌, 상표권 기반 분쟁 | ⭐⭐⭐⭐ 느림 |

- **UDRP** 가 유일하게 "결국 도메인이 우리 것이 되는" 경로지만, **구매가 아니라 상표권 분쟁**이다.
  gowid 상표가 등록돼 있으면 "우리 상표를 사칭했다" 고 주장해 회수할 수 있다.
- **현실 순서**: Railway 신고(빨리 내림) + Safe Browsing(사용자 보호) → 안 되면 도메인 정지/UDRP.

### 도메인 구매가 의미 있을 때 → 예방 (defensive registration)

공격 전, **아직 아무도 안 가져간 유사 도메인을 선점**할 때만 구매가 의미 있다.
- 예: `gowid.co.kr`, `gowid.net`, `gowid.io`, `gowid-card.com`, `gowid-login.com`
- 한계: 조합이 **무한대**라 전부는 못 산다. 이미 선점된 `gowid.co.com` 은 애초에 못 산다.
- 실무: **핵심 몇 개만 선점 + 나머지는 모니터링으로 잡아 신고.**

---

## 6. 실무 대응 체크리스트

- **증거 수집** — 스크린샷, WHOIS, DNS 기록, HTTP 헤더, SSL 인증서 (신고·법적근거용). 접속은 격리 환경에서.
- **플랫폼 abuse 신고** — Railway → Cloudflare → 도메인 registrar 순.
- **Google Safe Browsing 신고** + (광고로 퍼지면) **Google Ads 상표권/피싱 신고**.
- **고객 공지** — 공식 채널로 "공식 주소는 `gowid.com` 뿐" 안내.
- **법무/상표** — 상표 등록 시 UDRP 또는 침해 통지.
- **선제 방어** — 핵심 유사 도메인 선점, 이메일 사칭 방어(SPF/DKIM/DMARC) 점검.
- **지속 모니터링** — Certificate Transparency 로그, `dnstwist` 등으로 유사 도메인 자동 감시.

---

## 핵심 요약

- **이미 생긴 `gowid.co.com`** → 구매❌, **신고로 내리기**(Railway / Safe Browsing / registrar) + 상표 있으면 UDRP로 회수.
- **아직 안 뺏긴 유사 도메인** → **미리 구매**로 예방 (전부는 불가 → 모니터링 병행).
- 트래픽 구조(Cloudflare 앞단 / Railway 호스팅)를 알아야 **어디에 신고해야 효과적인지**가 보인다.
